# PJR-HW09 移行後のアプリを人の目で通しで操作して確かめる

## 1. 概要

移行の後のアプリを、人が通しで操作して確かめていない。自動のテストで拾えない、操作の感触・表示の崩れ・文言の違いなどを、人の目で確かめる。

## 2. 完了条件

naoji の判断（2026-11-01）で、ほかの自動のテストで確かめている流れは人が繰り返さない。人が行うのは最低限の起動の確認だけとし、自動のテストで確かめていない流れは orchestrator が自動で確かめる。

- **最低限の起動の確認（人）**: 移行の後の版（`feature/frontend-test-upgrade` の先頭）を docker compose で起動し、ホストのブラウザーで `http://localhost:30000` を開き、トップからかんたん見積もりの結果まで 1 回通して、表示と操作に目立った問題がないことを確かめる。結果を「4. 対応結果」に記録する。
- **自動の確認（orchestrator）**: 手順書（3.1）の 12 の流れのうち、ほかの自動のテストで確かめていない次の 3 つを、移行の前（`develop`）と後で同じ操作をして比べ、違いがないことを確かめる。
  - No 5 災害のモードをトップから結果まで（質問と答えの順、結果の画面）。
  - No 7 共有（共有リンク、QR コード、リンクを開き直した結果）。`qrcode.react` が 3 から 4 に上がったため。
  - No 8 画像で保存（保存された画像）。Chakra UI・Emotion の更新の影響を受けうるため。
- ほかの 9 の流れは、次の自動のテストで確かめている: E2E（トップ・規約・かんたん／くわしく見積もり）、単体テスト（答えの復元・入力の境界・計算 API の失敗・共有リンクの符号化）、story と Browser Mode（結果の開閉・キーボード・エラー画面）、見た目の比較（PJR-HQBE、13 画面）。
- 問題が見つかれば、別の項目に分ける。

### 3.1. 手順書（2026-11-01、specdojo-orchestrator）

**準備**

1. `../OpenFisca-Japan` で、移行の後の版（`feature/frontend-test-upgrade`、2026-11-01 時点の先頭は `0134bda`）を checkout する。項目を流していないときに行い、終わったら元のブランチに戻す。
2. `docker compose up --build -d` で起動する（API は 50000、画面は 30000）。または `dashboard` で `npm ci` と `npm run dev`。
3. PC のブラウザーで `http://localhost:30000` を開く。スマートフォンは、実機（同じネットワークから）か、ブラウザーの開発者ツールの端末の表示で確かめる。
4. 移行の前の版を 30001 で並べて起動する（次の「移行の前と並べて比べる」）。

**移行の前と並べて比べる**（2026-11-01 追記）

移行の前の基準は、手元の `develop`（`823818e`）とする。公開されているサイト（`main` の `1f8d13d` から作られている）は、`develop` にある `dashboard` の 8 件の commit（計算の表示のラベル、小さい画面の見出し、Safari の全角の数字の入力、共有 URL の短い符号化など）を含まないため、違いが移行によるものか見分けられない。また本番の API を呼び、本番の利用の記録に試しの操作が混ざるため、移行の前の基準には使わない。

```bash
cd ../OpenFisca-Japan
git worktree add --detach ../OpenFisca-Japan-before develop
cd ../OpenFisca-Japan-before/dashboard
docker build -t ofj-dashboard-before .
docker run -d --name ofj-dashboard-before -p 30001:30001 ofj-dashboard-before \
  npx vite --port 30001 --strictPort --host 0.0.0.0
```

- 移行の前は `http://localhost:30001`、移行の後は `http://localhost:30000` で開き、左右に並べて同じ操作をする。スマートフォンの大きさで見るときは、両方の開発者ツールで同じ端末の表示にそろえる。
- どちらも計算 API はブラウザーから `localhost:50000`（compose の `openfisca`）を呼ぶ。
- 移行の前の開発サーバーは、コンテナの中でも 30001 で起動する。Dockerfile の既定（`npm run dev`、30000）のままだと、HMR の WebSocket がホストの 30000（移行の後の画面）につながろうとして `WebSocket connection to ws://localhost:30000 failed` になるため。
- ホストのブラウザーでは `localhost` で開く。移行の後の Vite 8 の開発サーバーは、知らないホスト名（`host.docker.internal` など）からのアクセスを 403 で断る（`server.allowedHosts`）。
- 移行の前の画面は `docker run` で動かす。compose はネットワーク名（`openfisca`）とポート（30000）が決め打ちで、2 つ目を起動するとぶつかるため。ソースは mount しない（build したときの中身で動く）。
- 片付け: `docker rm -f ofj-dashboard-before`、`docker rmi ofj-dashboard-before`、`../OpenFisca-Japan` で `git worktree remove ../OpenFisca-Japan-before` と `git switch develop`。

## 4. 対応結果

**自動の確認**（2026-11-01、specdojo-orchestrator）

- 方法: このリポジトリの `tools/visual-compare/flows.mjs`（`605a422`）で、移行の前（`develop`、`823818e`）と後（`0134bda`）をそれぞれ build し、`vite preview` で同じポート（127.0.0.1:30110）に順に起動して、同じ操作を流した。計算は compose の API（`host.docker.internal:50000`）に送った。日時は 2026-01-15 に固定し、アニメーションを止めた。
- 最初の実行では、移行の前だけ災害のモードの 7 問目（人数の入力欄と「いいえ」のある質問）で止まった。操作の側が入力欄の名前（PJR-4SM2 で移行の後にだけ付いた `aria-label`）で入れる値を変えていたためで、アプリの違いではない。人数の質問は両方で「いいえ」を選ぶよう操作を直し、流し直した。

| No  | 流れ                             | 結果                                                                                                                                  |
| --- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 5   | 災害のモードをトップから結果まで | 両方とも 11 問で結果に着き、質問と答えの順が一致した。結果の画面の文字が一致し、画面の画像（1280×1647）は画素の差が 0                 |
| 7   | 共有                             | 共有リンクの URL が一致し、QR コードの画像（200×201）は画素の差が 0。リンクを新しいページで開き直した結果の文字も、元の結果と一致した |
| 8   | 画像で保存                       | 保存された画像（640×1803）は画素の差が 0。画像を開いて、結果・QR コード・ボタンが描かれていることを確かめた。ファイル名も一致した     |

- 3 つとも、移行の前と後で違いはなかった。

**最低限の起動の確認**（2026-11-01、naoji）

- 移行の後の版（`feature/frontend-test-upgrade` の `0134bda`）を docker compose で起動し（dashboard は Vite 8.3.5 で build されていることを orchestrator が確かめた）、ホストのブラウザーの `http://localhost:30000` で、トップからかんたん見積もりの結果まで通した。問題はなかった。
