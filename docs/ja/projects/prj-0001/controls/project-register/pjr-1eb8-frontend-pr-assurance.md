#### どの区切りでも行うこと

区切り 3〜6 のブランチは、区切り 2 の古い先端（`3f5eaaa`）の上に積んである。前の区切りの PR が上流で merge されたら、次の順で進める。

1. 手元の `develop` を上流の `develop` まで早送りする（フォークは naoji が sync fork する）。
2. 区切りの PR 用のブランチに `develop` を merge する。区切り 2 と 2.5 の変更（見た目の期待値・CI の `visual` の job・`build.target`・区切り 2.5 のテスト）がここで入る。衝突を解いたら、`package-lock.json` の整合を `npm ci` で確かめる。
3. 取り込んだあとの状態で、`npm ci`・`npm run test`・`lint`・`pretty:check`・`build`・`test:ui`（3 回）・`build-storybook`・E2E（2 回）を流す。出力の JS が ES2019 として読めること、Node.js 26 で build できることも確かめる。

5. `bash e2e/visual/docker.sh compare` で、更新の前の `develop`（`6e5a6c6`）の期待値と比べる。差が出たら、意図した変更か不具合かを判断し、意図した変更なら `capture` で撮り直して差分を PR でレビューしてもらう。
6. この note に区切りの節を書き、README の表を直し、PR の本文（`../OpenFisca-Japan/tmp/pr-<ブランチ>.md`）を用意する。push と PR は naoji が行い、CI（特に `visual` の job）を一緒に確かめる。

## 2. 背景・文脈

- naoji の依頼（2026-11-10）: 区切り 2 の PR を準備するにあたり、Vite などの更新の現行保証をどう担保しているかを確かめたところ、区切りごとに何がどのテストで保証されているかを 1 か所に残しておく必要があると分かった。区切りごとに 1 つの note に追記する。
- 出典の個票は、それぞれの項目を close したときの記録である。数字は出典の時点のもので、区切りのブランチに `develop` を merge したあとに確かめ直した場合は日付を書く。
