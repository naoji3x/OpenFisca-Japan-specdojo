# PJR-HQBE 移行の前後で主な画面のスクリーンショットを比べる

## 1. 概要

PJR-49V3〜BSXA の移行は、DOM・見えるかどうか・a11y・E2E で確かめたが、見た目（スクリーンショット）の比較をしていない。Vite・Chakra UI・framer-motion などの更新で見た目が変わっていないかを、移行の前と後で撮って比べる。

## 2. 完了条件

- 比べる 2 つの版: 移行の前（`openfisca-japan` の `develop`、`823818e`）と、移行の後（`feature/frontend-test-upgrade` の先頭。2026-11-01 時点は `378eb36`）。
- 撮る画面: トップ、規約・制限事項のダイアログ、かんたん見積もり・くわしく見積もり・災害のモードの最初の質問、主な質問テンプレート、結果（給付のみ・貸付のみ・両方・対象なし）、エラー画面（GenericError・FormResponseError・NotFoundError）。計算 API は固定の応答で返す。
- 画面の大きさ: PC（1280×800 程度）とスマートフォン（390×844 程度）の 2 通り。
- 毎回同じ結果になるよう、同じ Chromium とフォント、固定の応答、固定の日時、アニメーションの停止をそろえて撮る。同じ版を 2 回撮って、画素の差がないことを先に確かめる。
- **① 画素の比較**: 2 つの版の画像を画素ごとに比べ（Playwright の `toHaveScreenshot` か pixelmatch）、違う画素の割合を画面ごとに出す。しきい値（目安は 0.1% 未満）を決めて理由を記録し、しきい値に収まる画面を「違いなし」と機械的に判定する。
- **② 配置とスタイルの比較**: しきい値を超えた画面について、主な要素（見出し・ボタン・入力欄・ラベル・結果の金額・リンクなど）の位置と大きさ（bounding box）と、計算されたスタイル（色・背景色・フォントの大きさと太さ・余白・枠の丸み・表示の有無）を、2 つの版から取り出して比べ、差を機械的に記録する（例:「ボタンの背景色が A から B」「余白が 16px から 12px」）。
- **③ 分類**: 差の出た画面を、orchestrator が ② の結果と画像を見て「許容できる違い」「直すべき違い」「判断がつかない」に分け、理由を付ける。人（DEV）が確かめるのは「判断がつかない」と「直すべき違い」に限る。
- 画面ごとの ①（違う画素の割合）・②（要素とスタイルの差）・③（分類と理由）の一覧を「4. 対応結果」に記録する。画像そのものは上流のリポジトリに commit しない（置き場所を記録する）。
- 直すべき違いは、この項目では直さず、別の項目に分ける。
- 撮るための仕組み（スクリプトなど）を上流に残すかどうかを決め、理由を記録する。
- 上流の文書・コード・コメントに、登録簿の ID やリンクを書かない。登録簿との対応は commit メッセージの `Refs:` 行だけで取る。
- 保護された設定（`package.json`、`.github/workflows/**` など）の変更が必要な場合は、変更案を「4. 対応結果」に書き、反映は利用者の承認のもとで行う。依存の追加は、流す前に orchestrator が入れる（exec の executor はネットワークに出られない）。

## 4. 対応結果

**方法**（2026-11-01、specdojo-orchestrator）

- 比べた版: 移行の前は `openfisca-japan` の `823818e`（`develop`）、移行の後は `378eb36`（`feature/frontend-test-upgrade` の先頭）。それぞれ `npm ci` と `npm run build` のあと、`vite preview` で起動した。
- 撮る仕組みは、Playwright 1.64.1 の Chromium で画面を撮り、同時に主な要素（見出し・段落・ボタン・リンク・入力欄・ラベル・ダイアログ・画像）の位置と大きさ、計算されたスタイル（色・背景色・フォントの大きさと太さと種類・余白・枠の丸み・枠線・行の高さ）を取り出すスクリプトを、orchestrator の作業用のディレクトリに作った。上流のリポジトリには何も足していない。
- 条件をそろえた: 日時を 2026-01-15 12:00（JST）に固定、`reducedMotion: 'reduce'` と CSS でアニメーションと遷移を停止、GTM を止める、計算 API は `dashboard/src/mocks/calculate/*.response.json` の固定データを返す、`deviceScaleFactor` は 1。画像はページ全体を撮った。
- 撮った画面（13 画面 × PC 1280×800・スマートフォン 390×844 = 26 枚）: トップ、規約・制限事項のダイアログ、かんたん見積もりの質問 1〜3（住所・年収・配偶者）、くわしく見積もりの質問 1、災害のモードの質問 1、結果（給付のみ・貸付のみ・両方・対象なし）、計算 API の 500 のあとのエラー画面、ページが見つからない画面。
- **安定性の確認**: 移行の後の版を 2 回撮り、26 枚すべてで画素の差がないことを確かめた。
- **感度の確認**: 違う画面どうし（トップと規約のダイアログ）を比べると、違う画素は 51.2%、要素の差は 19 件と出た。違いがあれば検出できる。
- しきい値: 違う画素の割合 0.1% 未満、かつ画像の大きさが同じなら「違いなし」とした（pixelmatch の色のしきい値は 0.1）。上の安定性の確認で、同じ版どうしの差が 0% だったため、この値で取りこぼしは出ないと判断した。

**結果**

| 条件                                               | ① 画素の比較               | ② 要素とスタイル                                                                                             | ③ 分類             |
| -------------------------------------------------- | -------------------------- | ------------------------------------------------------------------------------------------------------------ | ------------------ |
| 外部のフォントを止めた（フォールバックのフォント） | 26 枚すべて 0%（違いなし） | しきい値を超えた画面がないため対象なし。例として結果（両方）の PC は、要素 23 個の位置とスタイルが完全に一致 | すべて「違いなし」 |
| 外部のフォントを読み込んだ（Noto Sans JP）         | 26 枚すべて 0%（違いなし） | 同上                                                                                                         | すべて「違いなし」 |

- 「直すべき違い」と「判断がつかない」はなかったため、DEV による確認（作業内容の No 5）と、別の項目への切り出し（No 6）は不要だった。
- 画像・要素の記録・比較の結果（`report.json`）は、orchestrator の作業用のディレクトリ（セッションの一時ディレクトリ）に置いた。セッションが終わると消える。
- 撮る仕組みは、今回は上流に残さない。上流に残すには、Playwright の `toHaveScreenshot` の基準画像の管理や、CI の環境とフォントの差の扱いを決める必要があり、この項目の範囲を超えるため。Chakra UI 3（PJR-ERDK）や React 19（PJR-6B0Q）の移行でも同じ比較を使うため、このリポジトリ（OpenFisca-Japan-specdojo）の `tools/` に残すことを提案する（利用者の承認待ち）。

**分かっていない点**

- 比べたのは Chromium だけである（WebKit・Firefox は PJR-1WNM）。
- アニメーションを止めて撮ったため、アニメーションの動き（framer-motion 10 → 11）の違いは比べていない。
- 質問は各モードの最初の数問だけで、くわしく見積もりの全部の質問は撮っていない。質問テンプレートは story と Browser Mode のテストで確かめている。
